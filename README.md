# 不用中间变量交换两个变量

配套 B 站视频的代码与实测。视频里出现的每一个数字，都能由这个仓库复现。

## 结论先说

这三种写法——加减法、乘除法、异或法——**不是三个技巧，是同一个格式的三次代入**：

```text
a ← f(a, b)
b ← f⁻¹(a, b)
a ← f⁻¹(a, b)
```

| 写法 | `f` | `f⁻¹` |
|---|---|---|
| 加减法 | `a + b` | `a − b` |
| 乘除法 | `a × b` | `a ÷ b` |
| 异或法 | `a ^ b` | `a ^ b` ← 自己是自己的逆 |

所以能不能交换，不取决于"记住了几种技巧"，而取决于 `f` 和 `f⁻¹` 是不是真的互逆。
**这个格式唯一的硬前提是：`a` 和 `b` 必须是两个互相独立的值。**

```bash
make run-all        # 三个实验全跑
make asm            # 汇编对照（需要 pwsh）
```

Windows：


## 三个反直觉的实测结果

### 1. 整数溢出之后，加减法**仍然换对了**

```text
int    before  2147483647 1
int    after   1 2147483647        ← 换对了
```

很多文章说"相加会溢出，所以加减法交换不可靠"。实测在补码机器上：

```text
a = a + b     2147483647 + 1        → -2147483648   (回绕)
b = a - b     -2147483648 - 1       →  2147483647   (回绕回来)
a = a - b     -2147483648 - 2147483647 → 1
```

加减在模 2³² 下互为逆运算，**回绕两次正好抵消**。

它仍然是隐患——有符号溢出在 C 标准里是未定义行为（§6.5p5），编译器有权做任何事——
但它不会像传说中那样当场失败。**真正会静默换错的是浮点数。**

### 2. 浮点数才是真的换不回来

```text
double before  0.10000000000000001 0.20000000000000001
double after   0.20000000000000001 0.10000000000000003
b restored?    no
```

`b` 拿到的是 `0.10000000000000003`，不是原来的 `0.10000000000000001`，差了 1 ULP。
这不是编译器的 bug，是浮点表示本身的固有性质——`0.1` 根本存不下精确值。

### 3. 编译器会看穿加减法和异或法

先把两个值取到互相独立的局部变量，再让 `gcc -O2` 编译：

| 写法 | 指令条数 | 与加减法是否逐字节相同 |
|---|---|---|
| 加减法 | 9 | — |
| 异或法 | 9 | **相同** |
| 中间变量 | 9 | **相同** |
| 乘除法 | 21 | 不同 |

编译器把前三种**归一成了同一段机器码**——它知道那三行等价于一次交换。
乘除法例外，除法代价高，化简不掉。

## 结论边界

**这个仓库里的所有数字都只在下面这个环境里成立，不是跨编译器的普遍规律：**

```text
gcc 4.9.4 (i686-posix-dwarf-rev0, MinGW-W64)   Windows 10 19045
```

明确不能从本项目推出来的结论：

- **"开优化后四种写法汇编都一样"是错的。** 准确说法是"两个值互相独立时，
  加减法/异或法/中间变量这三种会被归一；乘除法永远不会"。
  差别在别名：`compare_asm.c` 里的 `g_*` 组直接反复读写 `*p`/`*q`，
  编译器不敢假设 `p`、`q` 不重叠，必须每次重新载入——**四种写法生成四段不同的汇编**。
  独立实测还显示 MSVC x64 `/O2` 下四种全都不同。
- **不能推出"所以应该用异或法"。** 异或法只对整数有效（浮点的存储方式做不了位运算），
  而且遇到同一个地址会把值清零。
- **不能推出"加减法很安全"。** 上面的"换对了"依赖补码回绕这个实现细节，
  语言标准并不保证。写代码时应该用中间变量。

## 同地址陷阱

```c
int x = 5;
swap_xor(&x, &x);   /* 之后 x == 0 */
```

第一行 `*p = *p ^ *q` 退化成 `x = x ^ x`，任何数异或自己等于 0。
后面的行再怎么算也救不回来。这不是极端边界情况——排序、去重、泛型容器里
`swap(&v, &v)` 都很常见。

**而且中招的不只是异或法。** `make run` 会把四种写法都在 `swap(&x, &x)` 上跑一遍：

| 写法 | `x` 的结果 | 为什么 |
|---|---|---|
| 中间变量 | **5** | 唯一安全的：`t = x; x = x; x = t` 本来就不动 |
| 加减法 | **0** | 第一行是 `5 + 5 = 10`，第二行 `10 - 10` 归零 |
| 乘除法 | **1** | 第一行是 `5 * 5 = 25`，第三行 `25 / 25` 得 1 |
| 异或法 | **0** | 第一行是 `5 ^ 5`，异或自己是 0 |

所以「`a` 和 `b` 必须互相独立」是**这个格式的共同前提**，
不是异或法独有的注意事项。视频里用异或法演示，只是因为它最好画。

乘除法还多一种失效模式：`b == 0` 时直接除零崩溃，`a * b` 溢出也会算错。
自检表里的 `n/a` 就是这些前提不满足的格子。

## 实际写代码该用哪种

**用中间变量。** 它任何时候都对；而且上面第三个实验说明，
开优化之后编译器本来就会把加减法/异或法生成和它一样的代码——
你手写的"技巧"并没有换来更快的机器码，只换来了出错的机会。
